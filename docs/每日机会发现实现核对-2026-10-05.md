# 每日机会发现：当前实现与覆盖缺口

核对当前产品分支的 discovery-search、search、sources、matching、opportunity-digest、workflow、UI 与云端 monitoring。代码未修改；没有使用真实 Key、外部付费请求或私人资料。既有搜索专项测试 25/25 通过，证明授权、预算、轮转、取消与证据行为，不证明真实召回质量。

## 总体判断

当前是“有限搜索线索 + 已选公开页面检查 + 人工核对导入 + 本地匹配摘要”。搜索线索不自动读取原文，不自动创建岗位，也不直接进入机会摘要。完整自动发现链路及真实覆盖评测尚未完成。

## A. 每日偏好搜索

1. 默认关闭；需有效 Brave Search 自带 Key、开启连接，再确认偏好签名与每日预算。仅应用运行时执行，每分钟检查到期，每次运行前预留下一轮时间为当前时间+24小时；不保证固定每天某个时刻、不补发停机期间多轮。
2. 查询只取方案的必须条件及全局条件。路线采用企业“招聘 岗位”、考公“公务员 招录 公告”、事业单位“事业单位 招聘 公告”、考研“研究生 招生 简章”。没有方案路线时按允许的四路线展开。方案内方向等标签按硬编码别名展开；考研方向只用原始标签，全局非路线标签当前没有同样的别名展开。软偏好不参与生成查询。
3. 路线与单个标签分别组合，例如“招聘 岗位 \"软件\"”和“招聘 岗位 \"上海\"”，不把全部条件拼成很窄的交集。方案间和路线间轮转，但单方案内部的维度/别名仍按生成顺序推进。没有自动从毕业年份生成届别查询，也不默认加“校招”；不加发布日期限制，能保留存量线索，也会混入旧公告。
4. 默认预算4、可设1–10次；每日与手动搜索共享工作区滚动24小时20次上限。每次固定 Brave web/search，count=10，没有 offset 或其他搜索翻页，也未指定国家/搜索语言参数。每条最多10条，因此默认每天最多40条原始返回记录，去重/无效链接剔除后可能更少。
5. 发请求前推进轮转位置。单条请求失败会结束本轮，保留先前结果；失败条不会在当日自动补发，剩余查询留待下轮，避免不确定计费重放。取消、停用、偏好变化、重启都有保护。轮转走到末尾时当天不会回到开头用满剩余预算。
6. 结果仅保存标题、URL、摘要、查询/方案/路线证据及首次/最近发现时间。HTTPS 校验与去除 fragment 后按 URL 去重，保留 query 参数；不同追踪参数或镜像URL仍可能重复。相同查询跨方案仍可能各执行一次，去重发生在结果聚合阶段。
7. 用户在已保存线索中点击“读取原文并核对”，才进入来源读取。UI每页20条只是本地列表分页，不是供应商搜索分页。首次发现时间不是开放时间。

实测查询计划（没有网络）：企业+技术+上海+国企生成17条；增加2027届和校招关键词后19条。默认预算4时，连续正常运行至少约5轮/5天才能首次遍历。企业+技术的方向别名占前面多条；实际可用岗位数和召回率未知。

## B. 原文读取与已选页面检查

- 用户选择具体公开 HTTPS 页面；不携带浏览器登录，不执行页面 JS。只接收网页/JSON，不处理 PDF公告或Excel职位表，最多1MB/15秒，只允许同源跳转与可校验公网IPv4；动态页面、登录页、跨站跳转及部分网络环境会失败或要求手工处理。
- 通用提取识别 JobPosting JSON-LD；另有百度校招/实习公开 SSR 单页适配。没有通用正文语义岗位提取、链接爬取、列表-详情遍历、自动下一页。百度能够报告网站总量和当前页，但仍只读本页。
- 原文存证后生成 confirmations 待确认草稿；用户填写/核对单位与批次，再确认创建或逐字段更新。新记录默认 openStatus=unknown、statusVerified=false。页面空结果或读取失败不当作停止招聘。
- 通用解析主要保留标题/单位/地点/描述/编号/链接/日期，不自动形成完整方向、行业、性质、工作方式和资格字段。百度的方向/资格文本在 evidenceFacts/描述中，现入库映射也未自动完整转换为匹配用字段。
- 来源确认路径当前按企业单位建立记录，workflow 缺省路线为 enterprise；考公/事业单位/考研查询存在，不表示这条导入路径已完成对应路线适配。
- 本机最多启用20个具体页面，每个页面约24小时读一次；关注单位本身不会自动定位招聘入口或创建监控。页面内容有变化生成新的待确认草稿，不静默覆盖用户资料。

## C. 匹配与摘要

确认入库的 opportunities 才进入匹配：同维度任选、多维度必须、方案间并集、全局必须/排除；方向/关键词是字面包含及有限别名，不是全文语义检索。可靠资格冲突排除，未知保留待核实。原文未结构化字段常会进入“资格待核实”，无法稳定完成精细个性化。

摘要仅针对已入库岗位，区分新开放、新发现在招、存量补充、开放待核实和关注变化，并记录首次展示/摘要避免重复。这里的“存量补充”是分类能力，不能证明已有完整存量搜索。已经展示、收藏、计划或已投递的机会可能不再算首次摘要。

搜索、来源检查与摘要是独立调度，摘要不会等待搜索和人工原文核验完成。没有摘要不等于全网没有相关岗位；可能是没有搜索到、没读原文、没导入、已经展示或被条件过滤。

## D. 云端边界

云端为已选页监控，默认未启用，需要生产部署；每账号最多20页，约24小时一次，渠道为账号通知箱。当前 monitoring 调用通用 extractJobs，而不是含百度适配的 extractSource；不能认为本地专用适配自动覆盖云端。云端也没有每日偏好 web 搜索、自动发现新公司或遍历所有岗位。

## 覆盖风险优先级

| 层级 | 缺口 | 影响 |
|---|---|---|
| 检索 | 单供应商、第一页前10条、宽泛单维度词 | 排名靠后、未索引或新开放页面容易漏，无法给召回承诺 |
| 节奏 | 查询多而预算小、失败结束一轮、停机停止 | 某些查询延迟多天，短窗口岗位可能错过 |
| 原文 | 需逐条人工读取，动态/PDF/职位表未接通 | 已找到线索也未成为岗位 |
| 来源 | 缺少正式来源池、入口/分页/详情适配 | 关注公司不等于完整监测，列表第一页不等于全量 |
| 个性化 | 方向/资格未完整结构化，匹配非语义 | 相关岗位可能需人工补充，分路线效果不稳定 |
| 通知 | 摘要只看已入库，调度独立 | 搜索成功也未必当日推送岗位 |
| 评测 | 无独立100岗基准与连续观察结果 | 当前不知道漏多少、慢多久、每个有效岗多少钱 |

## 下一阶段建议

先固定企业校招首发范围（届别、方向、城市、20–30家公司），建立独立官网人工基准并覆盖所有分页，不用系统搜到的结果当基准。

并行接“官方入口与列表/详情适配”及“定向搜索补充”，记录每家公司/页/查询覆盖和失败。完善有限分页、查询组合/同义词分配、跨方案查询去重、关注/临近截止优先与失败补查。任何改变付费重试、预算和发送范围的行为都保留明确授权。

补上搜索URL→原文证据→提取候选的批处理，保留不确定开放与资格事实给用户确认；支持动态公开页及PDF/职位表的专用解析，并正确入库路线和匹配字段。

随后按至少100条人工岗位、连续7天测量来源可用率、有效岗位召回、相关机会误过滤、发现延迟、重复/误合并及有效结果成本。达标后再确定产品可承诺的覆盖范围。完整搜索无法在没有定义范围和基准时被证明。
