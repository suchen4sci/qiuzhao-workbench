## 审查期间发现并复核修复

1. **P2：过时反馈会静默确认新版本。** 原反馈和变更已读 API 未校验机会版本；打开旧表单后岗位变更，提交会将未见过的新版本设为反馈依据。最新两条 API 强制当前岗位 revision，UI 传快照/弹窗版本。旧反馈、旧 ack 和无版本 ack 均拒绝且不产生写入。
2. **P2：标签排序造成误判重大变化。** 原 fingerprint 保留集合顺序，北京/上海顺序互换即解除忽略。最新 route/city/direction/industry/nature 去重并排序；复现用例通过。
3. **P2：变更无法从界面确认已读。** 原仅有 acknowledge API，UI 无调用。最新卡片出现“确认已核对变化”按钮，携带 revision 调用 opportunity-change-read，刷新列表；同版本提示消失，再次改变截止又产生新提示。
4. **P3：恢复后的反馈仍触发变更提示。** 原 kind=none 也计算 changed，恢复后仍出现反馈变更提示。最新 none 不参与 changed；修改截止后仍无伪提示。

## 已验证边界

- 三种反馈类别合法；条件不符要求原因；错误类别、非文本/超长原因、非法天数均拒绝，且不写反馈。
- 反馈保存到独立 feedback 字段，保留 applied 用户状态以及已有计划/申请的完整记录。
- 用户隐藏以 filterOrigin=user 表示，资格匹配保留在 qualificationMatch；恢复用户反馈后仍须通过当前资格判断。修正个人学历事实后才按新事实重匹配。
- 不感兴趣/条件不符隐藏本岗位，不影响同单位另一个岗位；已看过保持可见。
- 七天反馈在精确到期边界自动失效；永久反馈遇到指纹重大变化重新可见。确认变更已读只消除重复提示，不重新隐藏岗位。
- 改抓取依据/描述包装/lastVerifiedAt 不解除已有反馈；标签集合排序变化不构成重大变更。
- 旧 state=ignored 数据仍隐藏，可通过恢复转换为新反馈状态；新反馈不删除计划/投递记录。
- 真实 OpportunityBrowser.browse 默认列表排除隐藏项，excluded 视图包含它，恢复后重新进入默认推荐。
- UI 原因采用 HTML 转义；表单保留原因输入，提供 7 天/30 天/关键变化或手动恢复；显示资格过滤仍有效。变更确认有明确用户动作。

## 非阻塞改进（P3）

反馈弹窗的 kind 和有效期每次默认“不感兴趣/7 天”，没有按现有反馈预选。若用户只是改原因，应注意避免无意改变“已看过”或永久忽略设置。建议编辑已有反馈时按保存值预选；尚无反馈时保留当前默认。
