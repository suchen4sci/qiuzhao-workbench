## 发现并修复

1. **用户恢复后的事件仍被自动改动。** 原 automaticUpdate 只看 event.source；规则创建事件经手动取消/恢复、完成/撤销完成后 source 仍为规则，允许后续自动改。最新 taskStatus 将事件标为 manual；自动取消完成后由 mail 自己明确重标规则来源。两条真实服务路径用例通过。
2. **取消通知撤回/作废被执行成取消。** 原取消词可匹配，但缺少相反语义保护。最新撤回、作废、恢复、照常、更正等进入人工核对；相关用例不再 structuredUpdate。
3. **“没有 ISO 时间”被当作“没有日期”。** 原取消含 date-only、改期含一有效 ISO 加另一无效或自然语言时间也可能自动执行。最新检测残留/无效时间，自动创建和更新均降为人工核对；date-only、非法月份、明天及新建多日期用例通过。
4. **终面线程误改一面。** 同线程一面事件收到“公司面试（终面）改期通知”原会自动改动一面。最新明确 final 标记并与既有事件比较；轮次冲突不自动执行。独立真实邮件 ingest 用例保持原事件不变。
5. **中文轮次截断和“最后一轮”伪造第一轮。** 最新完整解析中文 1–20，十一不再被取为一；超限或未明确映射的初面/复试等保守待确认。“最后一轮”只表达 final，不生成 round=1。边界用例通过。

## 已验证的安全边界与行为

- 单独 opt-in autoUpdate；关闭该项后跟进邮件保持 pending，不因为开启 autoCreate 而重复创建既有线程事件。
- 必须同连接、同发件地址且 references 唯一对应事件；不同 sender、不同邮箱连接、同线程关联两个事件均不更新。
- 只有规则创建、仍 scheduled 且任务 pending 的事件可自动处理。手改事件、已完成事件、用户取消后恢复、完成后撤销完成均保持不变。
- 新邮件的 Date 发件与 mail_server 收件都必须严格晚于全部既有事件关联邮件；相同或倒序时间保持 pending。
- 既有 endsAt 存在时不能只自动移动 startsAt，以免保留旧结束时间形成错误区间。
- 清晰改期只修改同一事件，保留历史 evidenceId 与关联邮件集合，任务继续 pending，没有完成 Activity。
- 清晰取消只改 cancelled 并撤销 pending reminders，不写完成记录。
- 自动更新最后一步确认写入失败时，邮件、确认、事件修改同事务回滚；不会留下半更新状态。
- 待确认 UI 已将 proposal.round 预填为轮次，并显示明确终面 checkbox，保存时传 final；选择既有事件时回填既有 round/final，不因未确认的新轮次描述擅自覆盖。已复核当前源码。
- UI 将自动创建与自动更新设为两个独立选项，并说明范围、附件/不确定通知待核对、不自动完成。选定发件地址是字符串规则，不是发件身份真实性验证。
