# F2.2 / F2.3 推荐反馈与每日摘要缺口审查

日期：2026-10-03。只读审查业务实现，仅新增本报告。对照 `docs/产品实施Plan-v1.md` 第 69、110、119–122、374 行；实现文件为 `workflow.cjs`、`reminders.cjs`、`workbench.cjs`、UI `workbench.js` 和 `opportunity-browser.js`。当前组筛选/单位聚合/批量计划工作不计为本组反馈和摘要的完成。

## 结论

当前存在机会匹配解释、查看已过滤、用户收录状态基础，以及每天一次的**任务行动摘要**。尚没有 Plan 要求的完整反馈闭环或每日**机会发现摘要**。以下为代码可直接确认的缺口，没有运行 UI 验收，也没有修改实现。

## 反馈闭环

|优先级|实际代码及缺口|用户影响 / 最小可验收行为|
|---|---|---|
|P2|`workflow.collect` 第 102–106 行只接受 saved/planned/applied/ignored/new，只有 state，没有原因、已看过、条件不符或反馈时间/依据版本|增加三类明确反馈和可选/适当必填原因，持久化后重开仍可复查；不能把岗位反馈扩展成行业或单位永久排除|
|P2|`recommendations` 第 234–236 行只附加 userState；`OpportunityBrowser.browse` 只按 match 过滤，不看 ignored|即便直接调用 collect(...,'ignored')，默认推荐仍展示。应让忽略按用户设定暂时退出默认推荐，同时保留完整复查入口|
|P2|机会卡和详情只有查看依据、加入计划；无反馈入口。collect 命令虽可用但未接 UI|卡片/详情可标不感兴趣、条件不符、已看过，显示当前反馈及原因，提供恢复|
|P2|“查看已过滤”只展示 match.included=false，并显示匹配原因；与用户 ignored 无关|用户过滤和资格过滤需可辨认。恢复用户忽略不能伪造资格通过；资格排除应引导修正事实/偏好/公告并重新匹配|
|P2|无用户反馈所对应的岗位版本、重大变化指纹、变更事件或重提示去重标识|截止、开放状态、资格等明确重大变化可单独提示一次；HTML 包装变化、重复同步、摘要重算不能解除忽略或重复提示。仍须人工核验来源变化，不自动覆盖手改机会|
|P2|`firstPresentedAt` 在第一次 collect（收藏/计划/投递）才写，不是实际展示时写；单位无首次展示记录|仅浏览但未操作的熟悉单位会无法识别；后台 snapshot/recommendations 也不应冒充实际展示。需要明确“展示/已读”的记录动作与幂等标识|

**已存在，不应重复实现：** 每次 recommendations 都读取当前资料和偏好并调用 matchOpportunity，现有机会字段更新后下一次快照会重新匹配。明确排除理由、资格待核实、已核验资格失败及方案命中已能解释；缺的是反馈覆盖层、可追溯版本与 UI 闭环。

另需避免将单一 state 同时用作反馈和投递生命周期：planned/applied 已由计划/投递动作写入。若反馈也简单覆盖 state，可能使“已投递”在推荐卡上退回“新”。反馈应与已有计划/申请关系保持一致，恢复反馈不得删除实际计划/申请记录。

## 每日机会摘要

|优先级|实际代码及缺口|最小可验收行为|
|---|---|---|
|P2|`reminders.cjs` 第 40–47 行只遍历 pending tasks，生成“待办 N 项”及 taskIds|新增机会摘要数据；可与行动摘要合并一份通知或清晰区分内容，不能把任务总数当新岗位数|
|P2|无新增时间窗、机会分类或 opportunityIds|每条推荐唯一分类：有可追溯开放日期且本窗口开放 → 新开放；确认在招但开放日期未知 → 新发现在招；确认在招且已知早于窗口开放 → 存量补充；开放无法确认 → 待核实。日期采集时间不能替代开放日期|
|P2|无单位首次推荐/岗位首次推荐/摘要已投递标识，只有任务摘要按时区+日去重|首次向用户展示单位才算新单位；已见单位新增岗位归“熟悉单位有新岗位”；同单位多岗、多个批次、重复来源各自正确去重。机会数、单位数、变化事件分开统计|
|P2|source 内容变化只会生成待核对草稿，不提供关注变化事件；摘要不读 watches、sources 或旧版本|单独展示可追溯关注变化，保持尚待核验标记。不要把来源读取成功、页面包装变化等当招聘重大变化，也不能静默改已入库岗位|
|P2|通知记录 UI 只有内容和“标为已读”，没有查看全部/加入计划/不感兴趣|摘要详情能查看完整对应集合，并逐条反馈或加入计划；摘要展示上限不能截断持久化候选或影响完整列表|
|P2|无机会去重投递窗口，无法区分今天没新机会和今天重新汇总旧机会|连续两天无新变化应真实显示无新增，仍可查看在招存量。下次摘要不能因重复抓取/重开应用重复宣传旧机会为新增|
|P3|现有偏好支持 hour、enabled；reminders 支持 app/native 开关，但没有可调整频率，亦无已授权外部摘要渠道|明确本机每日一次能力；若按完整 Plan 验收，应支持频率选择和授权渠道。不得因补此功能默认向外部服务发消息|

**已存在，可复用：** 每日按时区/日期去重、默认摘要开关、小时配置、应用内投递留痕、可选系统通知状态、关闭后不重复自动重发。独立面试/截止提醒应继续保持独立，不应因机会摘要节流而丢失。

## 建议验收用例

1. 三类反馈保存原因，重启保留；恢复后重新可见；单岗位不感兴趣不影响同单位其他岗位。
2. 直接调用反馈 API 后默认列表与复查列表一致；反馈不覆盖已计划/已投递事实。
3. 资格失败的机会恢复用户反馈后仍为资格排除；修正个人事实后重新匹配进入对应层级。
4. 同一忽略机会重大变化只提示一次；包装变化不提示；确认/忽略变更后不无限重复。
5. 一家新单位两个岗位只计一家单位；次日第三岗位计熟悉单位新岗位；另一批次和重复来源不能制造新单位。
6. 一个窗口覆盖新开放、未知开放日期但核验在招、早期开放存量、开放待核实各一条，各归唯一类别；不可依据 firstSeenAt 判断新开放。
7. 摘要仅展示前三项时，“查看全部”仍返回所有候选；可以加入计划和不感兴趣，已存在计划不被改期。
8. 同日反复调度、停机恢复及第二天重复来源不重复计新增；无新机会如实显示，并保留存量入口。
9. 未启用外部渠道不产生任何外部发送；关闭摘要不影响单独开启的面试/截止提醒。

来源覆盖的 100 岗位 / 7 天门槛仍未满足；反馈和摘要实现不改变这一限制。
