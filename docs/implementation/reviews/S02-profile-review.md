## 待修复发现

### P2：主资料损坏时无法通过历史恢复

位置：`profile-service.cjs` 第 48、64–67 行。

重现：读取版本 A → 保存 B（A 已进入历史）→ 将 profile.json 改成截断 JSON `{truncated` → 调用 `restore(A.hash, B.hash)`。实际返回 JSON 解析错误，原因是 restore 复用 save，而 save 必须先成功解析当前资料。主文件缺失时同样不能恢复。

建议：为故障恢复提供明确的服务入口，先保存当前原始损坏字节为隔离备份，校验选定历史资料与当前原始状态后原子恢复；不跳过常规保存的并发保护。GUI 提供恢复入口，不要求用户手改文件。

### P2：一条损坏历史阻止浏览全部正常版本

位置：`profile-service.cjs` 第 59–62 行。

重现：在历史目录写入名字符合 64 位 hash 的截断 JSON 文件；`history()` 整体抛出解析错误，无法列出正常版本。

建议：逐条校验并将损坏版本标注为不可恢复，正常历史继续展示；避免因一条坏记录封锁恢复能力。

### P2：hash 检查与替换之间的外部写入可被静默覆盖

位置：`profile-service.cjs` 第 48–54 行。

重现方法：在最终 `fs.renameSync(temp, profile.json)` 前注入另一个写入者更新主文件；服务成功返回自己的版本，外部更新既未保留在当前文件也未进入修订。该注入模拟另一个应用实例或手工 JSON 编辑恰好发生于检查和替换之间，不是同进程同步调用的竞态。

建议：受支持的写入路径采用同一工作区锁/单写入者协议，替换前再次核验主文件状态；如不支持同时手工写文件，明确支持边界并检测文件变化。添加两个写入者的集成测试，确保迟到写入收到冲突错误。仅增加一次 hash 检查不能构成对不遵守协议的任意外部写入的绝对保证。
