# S13 托管账户、任务结算与支付独立审查

审查日期：2026-10-03。范围：`hosted-service/{store,accounts,jobs,payments,http,processors,server,admin}.cjs`。审查代理仅新增 `hosted-service/tests/review.test.cjs` 与本报告；业务修复由主实现代理完成。

结论：当前有限范围的离线服务层复审通过，13 项独立回归通过。本结论不代表托管商业服务已上线，也不代表 S13 端到端、真实商户和收退款流程已验收。没有使用真实 Key、真实模型供应商或真实支付渠道，没有进行正式部署。

## 已修复并复验的发现

1. **P1：所有报价都失败。** `quotes` 表只有六列，原 `INSERT INTO quotes VALUES` 使用七个占位符；实际运行时报 SQL 错误，任何付费任务均无法开始。已改为六个占位符；报价、预留、交付、退款相关回归通过。
2. **P1：退款和支付争议被静默忽略。** 原签名 webhook 只处理付款成功事件，退款/争议直接返回成功确认，已入账额度仍可消费且没有审计记录。现记录 `payment_alerts`，通过 payment intent 定位并冻结相关账户；冻结后新任务被拒绝，正在运行的任务返回结果时释放预留且不交付、不结算。这里的冻结是待人工核对，不是现金退款或自动账务冲正。
3. **P1：未知/乱序退款可能误伤全部客户。** 首次修复曾在找不到订单时冻结所有已付款账户。现仅保存待关联告警，付款事件到达后按同 payment intent 关联并冻结对应账户。独立测试证明无关付款客户不被冻结，先退款后付款最终冻结正确客户。
4. **P1：配置无法交付的服务仍可开放 live 支付。** 原启动门禁仅要求价格非空，`model.enabled=false` 或缺失模型名称时仍可能展示可购买套餐。现 live 启动需要 `liveAccepted===true`，并校验已启用、地址/模型配置完整且有 API Key。独立测试覆盖没有运营验收声明、模型关闭、缺模型名称，均阻止启动。
5. **购买确认范围加固。** 实现方补充了 checkout 的金额、币种、额度与当前套餐/历史订单匹配检查。测试覆盖任一字段变化时必须重新确认，且不会创建订单或调用支付供应商。

执行：`node --test hosted-service/tests/review.test.cjs`。Node v25.9.0，13/13 通过。每项使用临时 SQLite 数据库；模型输出与支付 HTTP 返回均由 fake provider 提供，签名由测试密钥本地生成。

| 账户与会话 | 邀请码错误拒绝、错误密码拒绝、邮箱归一化、服务端仅存 token hash、注销后 token 无效 |
| 越权 | 其他账户无法读取或取消任务 |

## 上线验收边界

- `LIVE_LAUNCH_ACCEPTED=true` 是运营方自行作出的验收声明，代码不会验证真实商户资质、生产 webhook 路由、模型可用性或服务交付质量。填写该变量不能替代真实验收记录；本轮未授权/执行真实上线或收款。
- 支付退款当前采取账户冻结与持久化待办，未实现现金退款执行、额度自动扣回、部分退款比例计算或自动解冻闭环。运营方必须建立核对订单、处理告警、账务调整和解除冻结流程，再开放真实交易。
- 原生 HTTP 默认只监听 loopback，正式外网访问依赖正确部署 HTTPS。当前限流使用 socket.remoteAddress，没有可信代理 IP 配置；反向代理后的所有客户端可能共享每分钟 10 次登录及 120 次请求额度。这是明确的部署容量限制，不能把本地演示测试当多用户生产验收。
- 未完成真实模型/Stripe test 与 live 商户联调、异常重试/延迟回调、反向代理容量、安全运维与备份恢复演练。SQLite 与单实例锁限制应在部署中遵守。
- 桌面端连接、用户实际看到的费用/范围确认、支付跳转、到账刷新、结果本地保存与退款求助体验由客户端接入审查另行覆盖。本报告不替代该链路。

## 桌面托管接入补审（2026-10-03）

补审范围：`desktop/src/services/hosted.cjs`、workbench/main 接线与 `src/ui/workbench.js` 的 hosted 操作。新增 `desktop/tests/hosted-review.test.cjs`，目前 **14/14 独立离线测试通过**。这里使用真实本地 SQLite 文档存储、内存 fake vault 和 fake HTTP 响应；没有声称验证真实 macOS Keychain、Electron UI 点击或真实云端部署。

本轮已由实现方修复并复验：

- **跨账号旧响应。** 登录切换原先不推进连接世代，旧账户未完成的报价返回后会绑定新账户。现登录开始推进世代、取消旧请求，旧响应拒绝落地；服务地址切换同时清令牌与账号。
- **退出与新登录竞态。** 原 logout 等远程响应后才清本地状态，可能删除等待期间新登录账户的令牌。现立即清旧身份，捕获旧 token 仅用于撤销；旧请求结束不修改新身份。交错测试通过。
- **外部数值字段 HTML。** 原账户余额、套餐额度、账本变化值直接作为 HTML 插值，外部服务可返回字符串污染界面。现客户端验证账户、套餐和账本数值/结构，UI 数值另作转义；恶意 HTML 类型被服务层拒绝。
- **来源与任务绑定。** 原只验证引文是否出现在服务自报正文中，未检查来源是否在报价范围。现校验来源个数、顺序 ID、文本界限、与授权 URL 同 origin，并核对任务 ID、kind 和报价额度；已知 remoteId 不接受替换。引文仍需通过原文包含与个人经历授权校验。
- **提交结果 UI。** 原报价确认窗口忽略返回的任务状态，总是显示“任务已提交”。现区分终态失败与交付结果；动态执行实际 hostedQuote 函数，验证 failed 不显示成功提交面板。
- **空结果与状态倒退。** ready/refunded 未带完整结果且无既有本地简报时拒绝采纳；旧 running 响应不能覆盖已取消等终态。测试分别覆盖空 ready 与取消后晚响应。

补审确认的工作流：发送范围确认前不发报价请求；默认不发送经历，选中经历仅投影允许字段、排除独立联系方式与证明人字段；报价持久保存原 payload、quoteId、requestId，提交超时后保留 pending_remote；重建客户端后重试继续使用原始内容和请求标识，不重新读取变化的个人资料；成功简报绑定原本地面试且只插入一次。令牌只经 vault 保存，普通设置和任务记录不保存 token；HTTPS 根地址与显式本机 HTTP 边界测试通过。

仍需保留的边界：本轮恢复测试重建了客户端服务对象，但没有实际终止并重启 Electron 进程；真实系统密钥存储与远程 session 撤销联调未做；同 origin 来源校验允许同站重定向，不能由客户端独立证明服务提供的原文真实来自该站点。运营方的真实交付、支付与安全部署验收仍适用本报告前述限制。

## 最后补测

服务端新增两项独立回归后共 13/13 通过：任务 watchdog 即使面对忽略 abort 的 provider，也会按时释放预留，并拒绝之后返回的结果，不结算；丢失 checkout 响应的订单超过安全重试窗口（实现为 20 小时，测试推进 21 小时）后拒绝再次调用支付供应商，要求运营核对，不自动新建第二笔支付。桌面测试仍为 14/14。本审查合计 27 项离线回归通过。
